GLM-5.2 is here. Try the new Z.AI coding model for free on Token Station

GLM-5.2 just landed with a big claim: Z.AI says the new coding model is strong enough to sit in the same conversation as the frontier coding models developers already use.

The market noticed. Z.AI shares jumped about 50% around the GLM-5.2 launch, turning a model update into a broader AI infrastructure story.

But there is a practical problem for developers: the claim is still early, and public benchmark evidence is limited. If you are building with coding agents, you do not need another headline. You need to know whether the model can actually do useful work in your own workflow.

Now you can test it directly. Token Station exposes glm/glm-5.2, and you can try GLM-5.2 for free alongside kimi/kimi-k2.7-code and openai/gpt-5.5 behind the same API key.

So we ran a small Token Station Arena smoke benchmark and used the result to answer a practical question:

Where should GLM-5.2 fit in a real coding-agent stack?

The comparison is simple:

  • GLM-5.2: the new 1M-context Coding Plan option.
  • Kimi K2.7 Code: the cheap open-weights coding workhorse.
  • GPT-5.5: the closed frontier baseline.

The three-model map

Here is the positioning before we get lost in numbers.

glm/glm-5.2 is interesting because it enters the lineup as a 1M-context coding model with pricing low enough to test seriously. It is not the cheapest option, and we should not claim public benchmark wins without evidence. Its advantage is that it gives teams another high-context coding model to try in the same harness.

kimi/kimi-k2.7-code is the cost experiment. It is an open-weights Mixture-of-Experts coding model: 1T total parameters, 32B active, 256K context, and a very low price. It is the model you test when fan-out, subagents, code search, and routine implementation are burning most of your tokens.

openai/gpt-5.5 is the baseline. It is closed, expensive, and still the model many teams use as the “if this cannot do it, maybe nothing can” reference. The point is not to pretend every new model beats it. The point is to find the tasks where you no longer need to pay GPT-5.5 prices.

The first takeaway is simple: GLM-5.2 sits much closer to Kimi than to GPT-5.5 on price, while keeping a 1M context window.

On output tokens, GPT-5.5 costs about 6.8x GLM-5.2. On input tokens, it costs about 3.6x GLM-5.2. If your coding agent reads a lot of code, reruns long contexts, or delegates file inspection to subagents, that gap becomes real quickly.

The cached-input price is also important. glm/glm-5.2 is configured with cached input at $0.26 per million tokens. For repeated work over the same repository context, that gives it a specific angle: long-context coding sessions where the codebase does not change much between turns.

Why GLM-5.2 is worth testing

The cleanest pitch for GLM-5.2 is not “frontier killer.” It is:

1M context, coding-focused route, and a price point that makes long agent sessions easier to justify.

That is a useful position.

A lot of coding-agent cost comes from context, not final answer length. The model reads files, sees diffs, loads test output, receives tool summaries, and carries architectural context across turns. If a model gives you a 1M window at $1.40 input and $4.40 output, it belongs in the evaluation set.

Use GLM-5.2 for:

  • long-context codebase reading
  • implementation tasks that need more than 256K context
  • refactors where the model must preserve behavior across many files
  • repeated iterations where cached input can matter
  • an intermediate tier between Kimi and GPT-5.5

That “intermediate tier” is the key. You do not need to choose between the cheapest workhorse and the closed frontier baseline for every task.

Where Kimi K2.7 Code still wins

Kimi K2.7 Code remains the obvious workhorse when volume matters.

It is open weights, Modified MIT, 1T total parameters with 32B active, and only $0.95 input / $4 output per million tokens. For subagents, code search, routine implementation, parallel file reading, and cheap experiments, that is hard to beat.

The right question is not “GLM or Kimi?”

The right question is:

Does this task need 1M context, or can it fit inside Kimi’s 256K window?

If the answer is 256K, Kimi is the cheaper first try. If the task needs a larger repository view, GLM-5.2 becomes the more natural candidate before escalating to GPT-5.5.

Where GPT-5.5 still belongs

GPT-5.5 is the closed, expensive reference model.

That sounds negative, but it is actually a useful role. You want a high-end baseline in the stack. Use it when the problem is ambiguous, high stakes, or genuinely hard enough that cheaper models are not earning trust.

Good GPT-5.5 moments:

  • final architecture review
  • high-risk refactors
  • debugging where cheaper models loop
  • design tradeoff analysis
  • reviewing generated code before merge

But you do not need to start every session there.

A practical team can keep GPT-5.5 as the escalation model, not the default model for every tool call.

Benchmark result: all three models passed the deterministic coding tasks

After the first draft, we ran a live Token Station Arena benchmark across the three models.

Command:

cargo run --release -- benchmark \
  --tasks all \
  --models glm-5-2,kimi-k2-7-code,openai-gpt-5-5 \
  --runs 1 \
  --jobs 1 \
  --skip-judge \
  --skip-article \
  --timeout 1800 \
  --verbose

This was a small deterministic coding benchmark: 3 Rust tasks, 3 models, 1 run per task/model pair, 9 live runs total. The judge was skipped, so the result is based on required checks such as cargo test, cargo check, cargo clippy, and task-specific scripts.

Result:

  • GLM-5.2 (glm/glm-5.2): 3/3 tasks passed. Runner-reported total cost: $0.329516. Token Station gateway usage for the run window showed 37 requests, 127,525 tokens, $0.09.
  • Kimi K2.7 Code (kimi/kimi-k2.7-code): 3/3 tasks passed. The Claude Code runner did not report usable cost metadata for Kimi, but Token Station gateway usage showed 53 requests, 188,893 tokens, $0.20.
  • GPT-5.5 (openai/gpt-5.5): 3/3 tasks passed. Runner-reported total cost: $0.919945.

The benchmark does not prove that GLM-5.2 is “better than” GPT-5.5. It does show something useful: on these three coding tasks, GLM-5.2 passed the same deterministic checks as GPT-5.5 while the available cost signals were far lower than GPT-5.5. The runner-reported GLM cost was about 36% of GPT-5.5’s runner-reported cost, and the Token Station gateway usage window showed $0.09 for GLM-5.2 vs $0.20 for Kimi K2.7 Code. Kimi also passed all three tasks; for Kimi cost, use the gateway usage figure because the runner artifact did not return usable token/cost metadata.

Task-level matrix:

  • Add API endpoint: GLM-5.2 passed; Kimi K2.7 Code passed; GPT-5.5 passed.
  • Fix failing test: GLM-5.2 passed; Kimi K2.7 Code passed; GPT-5.5 passed.
  • Refactor pricing logic: GLM-5.2 passed; Kimi K2.7 Code passed; GPT-5.5 passed.

The honest takeaway is routing, not a leaderboard claim: all three handled the small suite, GLM-5.2 looked cost-effective against GPT-5.5 in reported runner cost, and Kimi remains attractive from the configured price table for high-volume work.

Use GLM-5.2 in Claude Code, Codex, and OpenClaw

The fastest way to evaluate GLM-5.2 is not to wait for a leaderboard. Put it into the coding tools you already use and run the same repository work you would normally give to GPT-5.5 or Kimi.

What you need:

  • A Token Station account: start from models.bytefuture.ai
  • Your Token Station API key, usually starting with gw-
  • Claude Code, Codex, or OpenClaw installed
  • The model id: glm/glm-5.2

Claude Code setup

Claude Code can route its Sonnet/Haiku tiers through Token Station. Keep GPT-5.5 as the escalation model if you want a frontier fallback, and run day-to-day coding work on GLM-5.2:

# Token Station endpoint + auth
export ANTHROPIC_BASE_URL="https://models.bytefuture.ai"
export ANTHROPIC_AUTH_TOKEN="gw-YOUR_TOKEN_STATION_KEY"

# Optional escalation tier
export ANTHROPIC_DEFAULT_OPUS_MODEL="openai/gpt-5.5"

# Default coding work on GLM-5.2
export ANTHROPIC_DEFAULT_SONNET_MODEL="glm/glm-5.2"
export ANTHROPIC_DEFAULT_HAIKU_MODEL="glm/glm-5.2"
export CLAUDE_CODE_SUBAGENT_MODEL="glm/glm-5.2"

claude

That makes GLM-5.2 the normal coding-agent route: main loop, subagents, repository reading, and test repair all use the same 1M-context model. When a task deserves the expensive baseline, switch to the Opus tier and let GPT-5.5 handle that part.

Codex setup

Codex uses one model per session, so configure Token Station as an OpenAI-compatible provider and make GLM-5.2 the default profile:

mkdir -p ~/.codex
cat > ~/.codex/config.toml <<'EOF'
model = "glm/glm-5.2"
model_provider = "token_station"

[model_providers.token_station]
name = "token_station"
base_url = "https://models.bytefuture.ai/v1"
env_key = "TOKEN_STATION_API_KEY"
wire_api = "responses"

# Optional escalation profile
[profiles.deep]
model = "openai/gpt-5.5"
EOF

export TOKEN_STATION_API_KEY="gw-YOUR_TOKEN_STATION_KEY"

codex                  # coding work on GLM-5.2
codex --profile deep   # escalation on GPT-5.5

This keeps the experiment reversible. If GLM-5.2 handles your normal code edits, keep it as the default. If a hard task needs more judgment, run that invocation with the deep profile.

OpenClaw setup

OpenClaw lets you make GLM-5.2 the primary model or use it specifically for subagents. The subagent route is useful when you want GPT-5.5 to supervise while GLM-5.2 does long-context fan-out work:

{
  "models": {
    "mode": "merge",
    "providers": {
      "token-station": {
        "baseUrl": "https://models.bytefuture.ai/v1",
        "apiKey": "${TOKEN_STATION_API_KEY}",
        "api": "anthropic-messages",
        "models": [
          {
            "id": "glm/glm-5.2",
            "name": "GLM-5.2 (Token Station)",
            "contextWindow": 1000000,
            "maxTokens": 128000
          },
          {
            "id": "openai/gpt-5.5",
            "name": "GPT-5.5 (Token Station)",
            "contextWindow": 1000000,
            "maxTokens": 128000
          }
        ]
      }
    }
  },
  "agents": {
    "defaults": {
      "model": { "primary": "token-station/openai/gpt-5.5" },
      "subagents": { "model": "token-station/glm/glm-5.2" }
    }
  }
}

To run the whole OpenClaw session on GLM-5.2, point agents.defaults.model.primary at token-station/glm/glm-5.2. Either way, the same Token Station key can run GLM-5.2, Kimi K2.7 Code, and GPT-5.5 side by side.

A practical model-routing strategy

Here is a simple way to route coding-agent work:

  1. Start with kimi/kimi-k2.7-code for cheap routine work.
  2. Move to glm/glm-5.2 when the task needs a larger 1M context or repeated repository context.
  3. Escalate to openai/gpt-5.5 for the hardest reasoning and final review.

That turns model choice from ideology into workflow design.

Kimi handles the volume. GLM-5.2 handles larger-context coding at a mid-tier price. GPT-5.5 stays available for the work where the premium is justified.
